## Exploitability Scale Reference

Every rule defines an integer exploitability rating ($0-5$) representing what an attacker
must possess to exploit the worst-case instance:

- **5 — Internet Unauthenticated**: Reachable from the internet with zero credentials.
- **4 — Guessable / Phishable**: Exploitable with phished/sprayed credentials or IDs.
- **3 — Authenticated**: Requires valid user/service credentials or tenant access.
- **2 — Elevated Foothold**: Requires foothold plus specific role or network elevation.
- **1 — Weakened Defense in Depth**: Impairs telemetry, audit, or defense-in-depth.
- **0 — Non-exploitable**: Informational hygiene / compliance with no direct attack path.

##### <a id="az-cmp-001"></a>`AZ-CMP-001` — Internet-facing virtual machine with an administrative port open

- **Severity**: `HIGH` | **Exploitability**: `4/5` | **Effort**: `~45 min`
- **Scope**: `per_resource`
- **Applies to**: `virtual_machine`
- **Compliance Mappings**: `CIS_AZURE_2.0: 6.1, 6.2` &bull; `GDPR: 5(1)(f), 32(1)(b)` &bull; `ISO_27001: A.8.20, A.8.22` &bull; `NIST_800_53: AC-17, SC-7` &bull; `NIST_CSF: PR.AC-3, PR.AC-5` &bull; `PCI_DSS_4: 1.3.1, 1.4.1` &bull; `SOC2: CC6.6`

**Description**: A virtual machine has a public IP address and a network security group that permits an administrative service from any source. Unlike an unattached NSG rule, this combination is directly reachable and therefore directly exploitable.

**Rationale**: This machine is routable from the internet and accepts administrative logins from anywhere. It is being scanned right now — internet-wide scans find a new public IP within minutes.

**Remediation**:
```bash
Remove the machine's exposure rather than only tightening the port rule.

1. Restrict the NSG rule's source to your VPN or office range (fastest mitigation).
2. Remove the public IP entirely and connect through Azure Bastion:
     az network nic ip-config update --name <ipconfig> --nic-name <nic> \
       --resource-group <rg> --remove publicIpAddress
3. Where occasional public access is unavoidable, enable just-in-time VM access in Microsoft Defender for Cloud so the port opens only on approved request.
```

##### <a id="az-cmp-002"></a>`AZ-CMP-002` — Virtual machine governed by no network security group

- **Severity**: `MEDIUM` | **Exploitability**: `2/5` | **Effort**: `~30 min`
- **Scope**: `per_resource`
- **Applies to**: `virtual_machine`
- **Compliance Mappings**: `GDPR: 5(1)(f), 32(1)(b)` &bull; `ISO_27001: A.8.20, A.8.22` &bull; `NIST_800_53: SC-7, CM-7` &bull; `NIST_CSF: PR.AC-5, PR.PT-4` &bull; `PCI_DSS_4: 1.2.1` &bull; `SOC2: CC6.6`

**Description**: No network security group applies to this machine, at its network interface or at its subnet. Nothing filters what may reach it from elsewhere in the virtual network, so anything that gets a foothold on the network reaches it directly.

**Rationale**: Segmentation is what turns one compromised machine into one compromised machine. Without a security group, an attacker who reaches any host on this network reaches this one too -- every port, from every peer -- and the lateral movement that follows is the difference between an incident and a breach.

**Remediation**:
```bash
Apply a network security group, preferably at the subnet so every machine in it inherits the same rules.

Start by denying inbound from the virtual network and allowing back only the ports this workload actually serves. Azure's default rules already permit all traffic within the virtual network, which is what this finding is about.

Azure CLI:
  az network nsg create --resource-group <rg> --name <nsg>
  az network vnet subnet update --resource-group <rg> --vnet-name <vnet> \
    --name <subnet> --network-security-group <nsg>

Use NSG flow logs first if you are unsure what currently talks to this machine.
```

##### <a id="az-cmp-003"></a>`AZ-CMP-003` — Virtual machine runs on unmanaged disks

- **Severity**: `MEDIUM` | **Exploitability**: `2/5` | **Effort**: `~120 min`
- **Scope**: `per_resource`
- **Applies to**: `virtual_machine`
- **Compliance Mappings**: `CIS_AZURE_2.0: 7.2` &bull; `GDPR: 32(1)(a)` &bull; `ISO_27001: A.8.24, A.8.3` &bull; `NIST_800_53: SC-28, AC-3` &bull; `NIST_CSF: PR.DS-1` &bull; `PCI_DSS_4: 3.5.1` &bull; `SOC2: CC6.1`

**Description**: A virtual machine has disks stored as VHD blobs in a storage account rather than as managed disks. The machine's data is then as safe as that storage account -- its keys, its network rules and whoever can list its containers.

**Rationale**: A managed disk is a resource with its own RBAC, its own encryption settings and no account key that unlocks it. An unmanaged disk is a file in a storage account, readable by anyone holding that account's key -- and Microsoft has retired unmanaged disks, so a machine still on them is also one living on borrowed time.

**Remediation**:
```bash
Convert the machine to managed disks. It needs a stop and a start.

Azure CLI:
  az vm deallocate --resource-group <rg> --name <vm>
  az vm convert --resource-group <rg> --name <vm>
  az vm start --resource-group <rg> --name <vm>

Delete the original VHD blobs once the machine is confirmed working -- until then they are a full copy of its disks in a storage account.
```

##### <a id="az-web-001"></a>`AZ-WEB-001` — Web app accepts plain HTTP

- **Severity**: `MEDIUM` | **Exploitability**: `2/5` | **Effort**: `~10 min`
- **Scope**: `per_resource`
- **Applies to**: `app_service`
- **Compliance Mappings**: `CIS_AZURE_2.0: 9.2` &bull; `GDPR: 32(1)(a)` &bull; `ISO_27001: A.8.24` &bull; `NIST_800_53: SC-8` &bull; `NIST_CSF: PR.DS-2` &bull; `PCI_DSS_4: 4.2.1` &bull; `SOC2: CC6.7`

**Description**: An App Service app answers unencrypted HTTP requests instead of redirecting them to HTTPS. Whatever a client sends on that first request -- a session cookie, a form, a token -- crosses the network readable.

**Rationale**: A site reachable over HTTP is one downgrade away from handing over its sessions. The fix is a single switch that makes App Service answer every HTTP request with a redirect, and no legitimate client needs the plain response.

**Remediation**:
```bash
Turn on HTTPS Only.

Azure Portal: App Service > Settings > Configuration > General settings > HTTPS Only: On > Save.

Azure CLI:
  az webapp update --name <app> --resource-group <rg> --https-only true

For a function app, `az functionapp update --set httpsOnly=true`.
```

##### <a id="az-web-002"></a>`AZ-WEB-002` — Web app negotiates TLS below 1.2

- **Severity**: `MEDIUM` | **Exploitability**: `2/5` | **Effort**: `~10 min`
- **Scope**: `per_resource`
- **Applies to**: `app_service`
- **Compliance Mappings**: `CIS_AZURE_2.0: 9.3` &bull; `GDPR: 32(1)(a)` &bull; `ISO_27001: A.8.24` &bull; `NIST_800_53: SC-8` &bull; `NIST_CSF: PR.DS-2` &bull; `PCI_DSS_4: 4.2.1` &bull; `SOC2: CC6.7`

**Description**: An App Service app accepts TLS 1.0 or 1.1. Both are deprecated, both have practical downgrade attacks, and every supported client already speaks 1.2.

**Rationale**: A minimum version of 1.0 does not mean clients use 1.0; it means an attacker positioned between them can make them. Raising the floor costs nothing for any browser or SDK released in the last decade.

**Remediation**:
```bash
Set the minimum inbound TLS version to 1.2.

Azure Portal: App Service > Settings > Configuration > General settings > Minimum Inbound TLS Version: 1.2 > Save.

Azure CLI:
  az webapp config set --name <app> --resource-group <rg> --min-tls-version 1.2
```

##### <a id="az-web-005"></a>`AZ-WEB-005` — Web app runs without a managed identity

- **Severity**: `LOW` | **Exploitability**: `1/5` | **Effort**: `~60 min`
- **Scope**: `per_resource`
- **Applies to**: `app_service`
- **Compliance Mappings**: `CIS_AZURE_2.0: 9.5` &bull; `GDPR: 32(1)(b)` &bull; `ISO_27001: A.5.17` &bull; `NIST_800_53: IA-5` &bull; `NIST_CSF: PR.AC-1` &bull; `PCI_DSS_4: 8.2.1` &bull; `SOC2: CC6.1`

**Description**: An App Service app has no managed identity, so anything it calls -- a database, a storage account, a key vault -- has to be reached with a secret stored in the app's settings.

**Rationale**: A managed identity is the difference between a connection string in an app setting and no secret at all. **Remediation**:

##### <a id="az-kv-001"></a>`AZ-KV-001` — Key vault can be permanently destroyed

**Remediation**:

- **Compliance Mappings**: `CIS_AWS_3.0: 5.2` &bull; `ISO_27001: A.8.20` &bull; `NIST_800_53: SC-7` &bull; `NIST_CSF: PR.AC-5, PR.DS-5` &bull; `PCI_DSS_4: 1.3.1` &bull; `SOC2: CC6.6`

**Description**: A security group allows a database port inbound from 0.0.0.0/0 or ::/0. The engine is then reachable by anyone who can guess a credential.

**Rationale**: A database exposed to the internet turns a leaked or weak credential into direct access to the data, with no other control in the way.


##### <a id="aws-net-004"></a>`AWS-NET-004` — A network ACL allows an admin port from the internet

- **Severity**: `MEDIUM` | **Exploitability**: `2/5` | **Effort**: `~25 min`
- **Scope**: `aggregate`
- **Applies to**: Aggregate (Tenant-wide)
- **Compliance Mappings**: `CIS_AWS_3.0: 5.1` &bull; `ISO_27001: A.8.20, A.8.22` &bull; `NIST_800_53: SC-7` &bull; `NIST_CSF: PR.AC-5` &bull; `PCI_DSS_4: 1.3.1` &bull; `SOC2: CC6.6`

**Description**: A subnet's network ACL admits SSH or RDP from 0.0.0.0/0. The ACL is evaluated before any security group, so it is the outer door — and unlike a security group it is stateless, which is why an over-broad one is usually written and then forgotten.

**Rationale**: Defence in depth is the whole argument for a network ACL: it is the control that still says no when a security group is edited wrongly. One that admits the internet has stopped being that.

**Remediation**:
```bash
Remove or narrow the entry:

  aws ec2 describe-network-acls --network-acl-ids <acl-id>
  aws ec2 delete-network-acl-entry --network-acl-id <acl-id> \
    --rule-number <n> --ingress

Network ACLs are stateless, so a replacement rule needs the return traffic allowed on the ephemeral port range as well — which is why the usual fix is to leave the ACL permissive and rely on security groups, and why this check is MEDIUM rather than HIGH.
```

##### <a id="aws-net-005"></a>`AWS-NET-005` — A default security group carries rules

- **Severity**: `MEDIUM` | **Exploitability**: `2/5` | **Effort**: `~15 min`
- **Scope**: `per_resource`
- **Applies to**: `network_security_group`
- **Compliance Mappings**: `CIS_AWS_3.0: 5.4` &bull; `ISO_27001: A.8.20` &bull; `NIST_800_53: SC-7, CM-7` &bull; `NIST_CSF: PR.AC-5` &bull; `PCI_DSS_4: 1.3.1` &bull; `SOC2: CC6.6`

**Description**: A VPC's default security group has ingress or egress rules on it. Anything launched without a security group named gets this one, so a permissive default is inherited by whatever somebody forgets to configure.

**Rationale**: The default group cannot be deleted and is applied by omission, which makes it the one group nobody chooses and everybody can end up in. Empty, it fails closed.

**Remediation**:
```bash
Strip it and use named groups instead:

  aws ec2 revoke-security-group-ingress --group-id <sg-id> --ip-permissions <rules>
  aws ec2 revoke-security-group-egress --group-id <sg-id> --ip-permissions <rules>

Check what is attached first — anything relying on the default will lose connectivity, and the fix for that is a group of its own rather than putting the rules back.
```

##### <a id="aws-sec-001"></a>`AWS-SEC-001` — A customer-managed key does not rotate

- **Severity**: `MEDIUM` | **Exploitability**: `1/5` | **Effort**: `~5 min`
- **Scope**: `per_resource`
- **Applies to**: `key_vault`
- **Compliance Mappings**: `CIS_AWS_3.0: 3.6` &bull; `ISO_27001: A.8.24` &bull; `NIST_800_53: SC-12` &bull; `NIST_CSF: PR.DS-1` &bull; `PCI_DSS_4: 3.6.1` &bull; `SOC2: CC6.1`

**Description**: A KMS key the customer manages has automatic rotation switched off, so the same key material protects everything it has ever encrypted.

**Rationale**: Rotation is one call and costs nothing: AWS keeps the old material so existing ciphertext stays readable, and new writes use the new key. Without it, material exposed once covers everything the key has ever protected.

```bash

```

##### <a id="aws-sto-001"></a>`AWS-STO-001` — S3 bucket allows public access

- **Severity**: `HIGH` | **Exploitability**: `5/5` | **Effort**: `~15 min`
- **Scope**: `per_resource`
- **Applies to**: `storage_account`
- **Compliance Mappings**: `CIS_AWS_3.0: 2.1.4` &bull; `GDPR: 5(1)(f), 25, 32(1)(b)` &bull; `ISO_27001: A.5.10, A.8.3` &bull; `NIST_800_53: AC-3, SC-7` &bull; `NIST_CSF: PR.AC-3, PR.DS-5` &bull; `PCI_DSS_4: 1.3.1, 7.2.1` &bull; `SOC2: CC6.1, CC6.6`

**Description**: A bucket does not block public access, or carries a policy that grants a wildcard principal. Anyone who learns or guesses the bucket name can read its contents without credentials.

**Rationale**: Publicly readable object storage is the single most common source of large cloud data breaches. It requires no exploit — the data is served to whoever asks.

**Remediation**:
```bash
Turn on the bucket's public access block, and remove any policy statement granting a wildcard principal.

AWS CLI:
  aws s3api put-public-access-block --bucket <bucket> \
    --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

Then check the policy:
  aws s3api get-bucket-policy --bucket <bucket>

Set the same four flags at the account level to stop it recurring:
  aws s3control put-public-access-block --account-id <account> \
    --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

Where content genuinely must be public, serve it through CloudFront with an origin access control rather than leaving the bucket itself open.
```

##### <a id="aws-sto-002"></a>`AWS-STO-002` — S3 bucket has no default encryption

- **Severity**: `MEDIUM` | **Exploitability**: `1/5` | **Effort**: `~10 min`
- **Scope**: `per_resource`
- **Applies to**: `storage_account`
- **Compliance Mappings**: `GDPR: 32(1)(a)` &bull; `ISO_27001: A.8.24` &bull; `NIST_800_53: SC-28` &bull; `NIST_CSF: PR.DS-1` &bull; `PCI_DSS_4: 3.5.1` &bull; `SOC2: CC6.1`

**Description**: A bucket has no default server-side encryption, so an object written without encryption headers is stored in the clear.

**Rationale**: Default encryption costs nothing and applies to every future object. Without it, whether an object is encrypted depends on whichever client happened to write it.

**Remediation**:
```bash
Set default encryption on the bucket.

AWS CLI:
  aws s3api put-bucket-encryption --bucket <bucket> \
    --server-side-encryption-configuration '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"aws:kms"},"BucketKeyEnabled":true}]}'

SSE-S3 (`AES256`) is the zero-effort option; a customer-managed KMS key adds an access-control boundary of its own and is worth it for anything sensitive.
```

##### <a id="aws-sto-003"></a>`AWS-STO-003` — S3 bucket accepts plaintext HTTP

- **Severity**: `MEDIUM` | **Exploitability**: `2/5` | **Effort**: `~15 min`
- **Scope**: `per_resource`
- **Applies to**: `storage_account`
- **Compliance Mappings**: `CIS_AWS_3.0: 2.1.1` &bull; `GDPR: 32(1)(a)` &bull; `ISO_27001: A.8.24` &bull; `NIST_800_53: SC-8` &bull; `NIST_CSF: PR.DS-2` &bull; `PCI_DSS_4: 4.2.1` &bull; `SOC2: CC6.7`

**Description**: A bucket has no policy denying requests made without TLS, so an object can be read or written over plaintext HTTP by anything that can reach the endpoint.

**Rationale**: S3 answers HTTP as readily as HTTPS, and nothing in the service refuses it. The only control is a bucket policy that denies the request, which is why this is a policy check rather than a setting.

**Remediation**:
```bash
Add a deny to the bucket policy:

  {
    "Effect": "Deny", "Principal": "*", "Action": "s3:*",
    "Resource": ["arn:aws:s3:::<bucket>", "arn:aws:s3:::<bucket>/*"],
    "Condition": {"Bool": {"aws:SecureTransport": "false"}}
  }

  aws s3api put-bucket-policy --bucket <bucket> --policy file://policy.json

Both ARNs matter: the bucket for operations on the bucket itself, and the wildcard for the objects in it.
```
